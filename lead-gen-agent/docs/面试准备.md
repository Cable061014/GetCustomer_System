# 面试准备手册 — AI 自动化获客系统

> 定位：实习面试 · AI 应用开发方向
> 用法：先通读一遍建立框架，再重点背「四、三个核心决策」和「七、数据点速记卡」。
> 原则：**面试官想听的是「为什么这么设计」，不是「你调了哪个 API」。**

---

## 一、30 秒开场版

> 「我主导做了一个 AI 自动化获客系统。业务上，输入『国家 + 行业』，它自动完成搜索客户、AI 分析、评分分层、生成开发信。
> 技术上，用 n8n 编排 20 节点工作流，串起 DeepSeek 和 SerpAPI。
> 但我觉得这个项目最有价值的地方，是我设计了一套『AI 提取事实 + 规则打分』的确定性评分引擎——因为 LLM 打分不稳定也不可追责，所以我把 AI 和打分职责分开，保证结果可解释、可回归。」

**要在这 30 秒里塞进三个数字**：20 节点、6 维度评分、13 条单测。

---

## 二、完整流程拆解（11 步）

| # | 步骤 | 做什么 | 工具 / 方法 | 作用 |
|---|---|---|---|---|
| 1 | 触发 | 输入目标市场 | n8n Manual Trigger + Set 节点 | 定「英国 + 路由器」这类参数 |
| 2 | 生成关键词 | 把「国家+行业」翻译成搜索词 | DeepSeek + Prompt | 覆盖不同客户类型与行业同义词 |
| 3 | 搜索客户 | 用关键词搜公司 | **SerpAPI**（Google 搜索 API） | 拿到候选公司列表 |
| 4 | 归一化去重 | 清洗、按域名去重、限流 | Code 节点（Node.js） | 避免重复分析同一家公司 |
| 5 | 抓取网页 | 拿公司官网内容 | HTTP Request 节点 | 获取分析所需的原始素材 |
| 6 | 提正文 | HTML → 纯文本 | Code 节点（正则去标签） | 降 token 消耗、去噪 |
| 7 | AI 分析 | 提取结构化字段 | DeepSeek + Prompt | 输出客户类型/规模/联系方式等 JSON |
| 8 | **确定性评分** | 打分分层 | **scoring.core.js**（Node.js 纯函数） | 6 维度加权 → high / medium / filtered |
| 9 | 导出 | 落盘 CSV | Convert to File + Read/Write File | 交付结果 |
| 10 | 生成开发信 | 给 high 客户写邮件 | DeepSeek + Prompt | 个性化开发信草稿 |
| 11 | 意向判断 | 判断客户回复 | DeepSeek + Prompt | 高意向→人工接管；退订→抑制名单 |

**流程一句话**：`一句话输入 → 搜客户 → 评分数 → 写开发信 → 判回复`
**人的参与点只有两处**：发信 + 谈价成交（刻意保留，AI 不替公司承诺价格与交期）。

## 三、关键选型对比（面试最常问的 4 组）

### 3.1 流程编排：n8n vs 其他

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **n8n** | 自托管免费、可视化编排、内置 HTTP/文件/重试节点、Code 节点可跑 Node.js | 复杂逻辑仍需写代码 | ✅ **选用** |
| 纯 Python 脚本 | 灵活、可控 | 流程要自己管调度/重试/错误处理，改流程成本高 | 早期快速验证可以，长期维护差 |
| Airflow | 调度能力强、适合数据 pipeline | 重、部署成本高、为 ETL 设计而非 API 编排 | 杀鸡用牛刀 |
| Zapier / Make | 上手快、连接器多 | 贵、私有化困难、复杂逻辑受限 | 成本与可控性不达标 |

**选择理由**：自托管零成本 + 可视化 + Code 节点能复用纯 Node.js 评分模块。是「编排用工具、逻辑用代码」的分工。

### 3.2 客户搜索：SerpAPI vs 其他

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **SerpAPI** | 封装好、返回结构化 JSON、免处理反爬、免费额度够测试 | 免费 100 次/月，超量要付费 | ✅ **选用** |
| 直接爬 Google | 免费 | 反爬、HTML 结构不稳定、易被封、法律风险 | 不可靠 |
| Google Custom Search API | 官方、稳定 | 免费额度更少、自定义引擎限制 100 站 | 灵活性差 |
| 必应搜索 API | 稳定、价格不同 | 结果质量与 SerpAPI 相近但生态略弱 | 备选 |

**选择理由**：需要的是「结构化搜索结果」，SerpAPI 直接给 JSON，省掉解析与反爬。

### 3.3 LLM：DeepSeek vs 其他

| 候选 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **DeepSeek** | 便宜、OpenAI 兼容、中文友好、国内直连稳定 | 生态与插件少于 OpenAI | ✅ **选用** |
| GPT-4o | 强、生态好 | 贵、国内需网络代理 | 成本不划算 |
| 通义千问 | 兼容 OpenAI、中文好 | 与本项目需求接近，属平替 | 备选 |
| 本地开源模型 | 免费、数据不出门 | **JSON 输出稳定性差**，本项目要求严格 JSON，小模型易破坏格式 | 风险高 |

**选择理由**：本项目最关键的成功条件是「LLM 稳定输出严格 JSON」。价格 + 兼容性 + JSON 稳定性三者平衡最优。
**加分点**：因为用的是 OpenAI 兼容协议，换供应商只需改 `baseUrl` + `model` 两个字段，代码零改动。

### 3.4 打分方式：确定性规则 vs LLM 直接打分

| 候选 | 说明 | 结论 |
|---|---|---|
| **AI 提事实 + 规则打分** | LLM 只提取枚举/布尔字段，加减分走固定规则 | ✅ **选用** |
| LLM 直接打分 | 把公司信息丢给 LLM，让它给 0–100 分 | 黑盒、结果飘、不可回归、无法追责 |
| 纯人工规则（不用 AI） | 全人工判断 | 无法规模化，正是要解决的问题 |

**选择理由**：见下一节，这是本项目最核心的设计决策。

## 四、三个核心设计决策（面试官最想听）

### 决策 1：评分用确定性规则，不让 LLM 直接打分

**问题**：LLM 打分有三个致命缺陷。
1. **不稳定** —— 同样输入，每次结果可能不同，无法复现
2. **不可回归** —— 改了 Prompt 不知道会影响哪些已有结果
3. **不可追责** —— 客户问「为什么我 85 分」，答不上来

**方案**：职责分离。
- **LLM 只做它擅长的**：提取**事实字段**（客户类型 = distributor、是否有进口能力 = true、规模 = medium），这些是枚举/布尔值，LLM 判得准
- **打分交给确定性规则**：6 维度加权，每分带 `reason` 可解释，改权重即调优，13 条单测保证改不坏

**收益**：结果稳定可回归、每分可解释、调优有依据。

### 决策 2：配置与代码分离 → 多领域通用

**做法**：把「会变的」和「不变的」分开。

| 类型 | 内容 | 存放位置 |
|---|---|---|
| 会变（业务规则） | 目标国家、行业、客户类型、评分权重、买卖信号 | `config/*.json` |
| 不变（逻辑） | 评分算法、工作流结构 | `scripts/*.js` |

**收益**：换行业 = 新建一个 ICP 配置文件 + 重新生成工作流，**不改一行代码**，10 分钟完成。已落地路由器、eSIM 两个领域。

**这个决策的价值**：它把「一次性项目」变成「可复用工具」。面试官问「你这项目能干嘛」时，这是最强回答。

### 决策 3：LLM 判枚举，不猜数字

**由来（真实踩坑）**：最初让 AI 填「员工数 / 营收」来评公司规模。结果 20 家公司**全是空**——因为公司官网几乎不写这些数字，AI 提取不到。而「规模」占 15 分权重，这一维度全拿保守值，**完全没有区分度**。

**重新设计**：引入 `sizeSignal` 规模代理信号，让 AI 判断枚举值 `large / medium / small / unknown`，依据是官网的**可观察信号**——是否连锁/多门店、产品线广度、有无批发入口、是否全国配送。

**提炼出的原则**：**LLM 不该被要求猜数字，应该被要求判枚举。** 数字字段 LLM 填不准（且倾向编造），枚举字段 LLM 判得稳。

## 五、模拟面试 Q&A（分层）

> 每题给「答题骨架」，不要逐字背，记住逻辑链即可。
> 【关键词】= 面试官想听到的点。

### 基础题

**Q1. 介绍一下这个项目？**
骨架：业务价值（一句话）→ 技术栈（n8n + DeepSeek + SerpAPI + Node.js）→ 核心亮点（确定性评分引擎）。
【关键词】自动化闭环、20 节点、AI 提事实 + 规则打分

**Q2. 你在项目里具体做了什么？**
骨架：主导架构设计 → 定技术选型 → 设计评分引擎 → 调试打通全链路 → 迭代优化（Prompt + 权重）。
诚实边界：「代码实现在我主导下、借助 AI 辅助完成，所以我对每一处的设计理由都清楚，也负责了全部调试和调优。」
【关键词】主导设计、技术选型、调试排错、诚实

### 设计题（核心，必问）

**Q3. 为什么评分不让 LLM 直接打？**
骨架：三个缺陷（不稳定/不可回归/不可追责）→ 职责分离（LLM 提事实、规则打分）→ 收益（稳定、可解释、13 条单测）。
【关键词】黑盒、可解释性、可回归、审计

**追问 3.1：那 LLM 提取错了怎么办？**
骨架：三层兜底 —— ①枚举封闭（AI 只能选我定义的固定值，不能自创）②宁缺勿猜（拿不准输出 `unknown` 走保守分）③数字字段不让 AI 填，改判枚举。
【关键词】枚举封闭、保守取值、格式约束

**Q4. 为什么用 n8n，不用你熟的 Python？**
骨架：任务性质是「流程编排 + 外部 API 调用」，n8n 更合适（可视化、内置重试/错误处理、改流程不动代码）；复杂逻辑仍写成纯 Node.js 模块，内联进 Code 节点。原则是「编排用工具、逻辑用代码」。
【关键词】编排 vs 逻辑、内置重试、配置与代码分离

**追问 4.1：n8n 里遇到过什么坑？**
骨架（挑 2 个讲，都是真实案例）：
- **配对链断裂**：节点做「去重 + 一对多展开」后，下游用 `.item` 表达式报「配对数据不可用」。原因是输出的 item 数量与上游对不上，n8n 的 item 追踪链断了。解决：改用 `.first()` 或按 `.all()[i]` 索引对齐，不依赖配对链。
- **文件访问被拒**：n8n 2.x 默认禁止文件节点访问任意路径，报「不允许访问该文件」。解决：加环境变量 `N8N_RESTRICT_FILE_ACCESS_TO=/data/exports` 白名单。
【关键词】item 追踪机制、安全白名单、定位过程

**Q5. 怎么做到换行业不改代码？**
骨架：配置与代码分离 → 业务规则全外置 JSON → 换行业只新建 ICP 配置 + 重新生成工作流 → 已落地 2 个领域。
【关键词】配置驱动、可复用、扩展成本

**Q6. Prompt 工程你具体做了什么？**
骨架：四类 Prompt 分工（系统提示词定人设规则、任务提示词定具体任务）。三个关键技巧：
1. **强制严格 JSON 输出**（`response_format` + Prompt 里明确「只输出 JSON」）→ 让 AI 输出能直接进流水线
2. **枚举封闭** → AI 只能选预定义值，防止乱编
3. **宁缺勿猜** → 拿不准输出 null，禁止用常识补全
【关键词】结构化输出、格式约束、防幻觉

### 追问 / 深度题

**Q7. 怎么保证改代码不会改坏？**
骨架：评分引擎写了 13 条单元测试（用 Node 内置 `node:test`，零依赖），覆盖：分层正确性、3 条硬过滤、风险标记、确定性（同输入两次打分完全一致）、分数边界（0–100）。改配置后跑测试 + 离线干跑。
【关键词】单元测试、确定性验证、回归

**Q8. 数据怎么存的？**
骨架：设计了 6 张表的 schema —— 公司表、评分历史表、联系人表、抑制名单表、发送日志表、审计日志表。
两个设计要点：①评分历史保留每次记录（可审计「这公司什么时候多少分」）②抑制名单独立且发送前必查（合规）。
用 SQLite：本地单机够用、零运维，schema 设计成可平滑迁移 Postgres。
【关键词】审计留痕、合规、可迁移

**Q9. eSIM 和路由器你都能做，效果一样吗？**
骨架（这是**边界认知题，答好了很加分**）：不一样，而且我从中得到了一个判断。
- 路由器是「**需求信号明显**」的品类 —— 分销商会主动在官网写「we distribute networking equipment」，搜索引擎能搜到
- eSIM 是「**需求信号隐藏**」的品类 —— 旅行社不会在官网写「我要卖 eSIM」，搜出来的全是同行供应商在招代理
- **结论**：搜索引擎获客打法适合「需求信号明显」的 B2B 硬件/贸易品类；对需求隐藏的数字服务，要换数据源（LinkedIn / 行业名录 / 展会名单）
【关键词】需求信号可见性、打法边界、换数据源

### 压力题

**Q10. 这项目有人真正用过吗？效果怎么量化？**
骨架（诚实 + 给可量化项）：
- 现状：跑通了英国路由器市场，搜到真实分销商并生成开发信；发信环节还在手动验证阶段
- 可量化：20 节点全自动跑通、2 家 high 客户精准命中、意向判断 6/6 准确、两轮评分调优（第一轮 3 家 high → 调优后 7 家）
- 不夸大：还没有真实的成交数据，因为冷邮件转化周期长
【关键词】诚实、过程指标、区分已实现与待验证

**Q11. 如果给你 3 个月继续做，你会怎么做？**
骨架（按优先级）：
1. **接邮件发送**（选邮件服务商 + 配 SPF/DKIM）→ 打通完整闭环
2. **提升数据质量**（搜索结果标题清洗、邮箱补全）
3. **做 RAG 客户知识库** —— 把抓取到的客户历史信息沉淀，用向量库做相似客户检索与个性化推荐
4. **加可观测性**（指标监控 + 失败告警）
【关键词】闭环、数据质量、RAG 延伸、可观测性

> 💡 第 3 点是把项目往你熟悉的技术栈（RAG / LangChain / 向量库）延伸的钩子，主动抛出来。

### 实习特有题

**Q12. 你一个大二学生，怎么想到做这个？**
骨架：在实习中发现获客靠人工重复劳动 → 想用 AI 自动化 → 从零调研选型、搭出原型 → 迭代两轮评分调优。

【关键词】具体认知、踩坑反思、能力边界

## 六、技术栈 gap 应对（重点准备）

### 风险

简历主线是 Python / FastAPI / Spring Boot / RAG / LangChain / Milvus，
但这个项目是 Node.js / n8n / DeepSeek。
→ 面试官很可能问：**「你自己熟悉 Python 和 LangChain，为什么这个项目用 Node.js 和 n8n？」**

### 答题框架（四步，把它转成加分项）

**第 1 步：坦然承认，不硬拗**
> 「确实，我平时主力是 Python 技术栈，这个项目用了 n8n + Node.js，是刻意的选型。」

**第 2 步：讲清选型逻辑（核心）**
> 「这个项目的本质是『流程编排 + 外部 API 调用』——调搜索 API、调 LLM、抓网页、写文件。
> 这类任务用 n8n 比手写 Python 更合适：可视化、内置重试和错误处理、改流程不用动代码。
> 而且 n8n 有 Code 节点，所以核心的评分引擎我还是写成了纯 Node.js 模块，逻辑部分是可控的。
> 如果用 Python 写，我得自己实现调度、重试、错误处理这一整套，投入产出比不划算。」

**第 3 步：反证能力（关键转折）**
> 「更重要的是，我不希望自己被单一技术栈绑住。技术选型应该看问题需要什么，而不是我会什么。
> 这个项目也证明了：换个语言、换个工具，我一样能把它做出来。」

**第 4 步：主动链接回熟悉的技术栈（钩子）**
> 「其实这个项目往后做，有个地方特别适合用我熟悉的技术栈 —— 我想加一个客户知识库。
> 把抓取到的客户信息沉淀下来，用 RAG 做相似客户检索和个性化推荐，这块用 Milvus + LangChain 就很合适。
> 相当于把两个技术栈合起来用。」

### 附：n8n / Node.js 核心概念速答

| 概念 | 一句话解释 |
|---|---|
| n8n 节点 | 一个功能块（调 API、写代码、读写文件）；节点间用连线传数据 |
| Code 节点 | 在流程里跑自定义 JS，本项目评分引擎内联在这里 |
| Trigger | 什么启动流程（手动点 / 定时 / Webhook） |
| item | n8n 里数据的最小单位，每个节点处理一批 item |
| HTTP Request 节点 | 发 HTTP 请求调外部服务（GET 取数据 / POST 提交数据） |
| JSON 在流程中的角色 | 节点间的通用数据格式，上一个节点的输出是下一个的输入 |
| `$env.XXX` | 在节点里读环境变量（本项目用它读 API Key，避免密钥写死在流程里） |

## 九、答题心法（最后看一遍）

1. **先讲为什么，再讲是什么** —— 面试官不关心你用了哪个 API，关心你为什么这么选
2. **主动暴露一个认知** —— 比如「LLM 该判枚举不猜数字」，比背功能列表更有记忆点
3. **诚实边界比完美更加分** —— 没接邮件发送、eSIM 不适用，如实说，实习面试看重的是判断力
4. **数字要有** —— 20 节点、6 维度、13 单测，具体数字代表你真做过
5. **答不上来就说思路** —— 「这块我没深入做过，但我的思路是……」比硬编强
